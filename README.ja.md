# JR Conventional-line Radio Receiver (JR 在来線デジタル列車無線受信アプリ)

[English](README.md) | 日本語

バージョン: **v1.7.0**

作者: KIRISHIKI Yudai <yudai.kirishiki@protonmail.com>

Rust・Tauri 2・SoapySDR で作った、JR 在来線デジタル列車無線の受信アプリです。
1 本の広帯域 IQ ストリームから **22 波を同時に復調し、波ごとに音声とデータを独立して復号**します。
製品名・バージョン・作者は、画面下部の「バージョン情報」で確認できます。

## はじめに

Rust（stable）、**SoapySDR 0.8 系の開発ライブラリ**、使用する SDR 用の SoapySDR モジュール、
[Tauri の OS 別の前提ソフトウェア](https://v2.tauri.app/start/prerequisites/)をインストールしてください。
フロントエンドは素の HTML / CSS / JavaScript なので、ビルドと実行に Node.js や npm は不要です。
UI のテストには Node.js 24.15 以降と `npm ci` を使います。

Ubuntu / Debian の例（パッケージ名はディストリビューションによって異なります）：

```sh
sudo apt install build-essential pkg-config libsoapysdr-dev soapysdr-tools \
  libwebkit2gtk-4.1-dev libgtk-3-dev librsvg2-dev libssl-dev
# 使用する機器のモジュール（soapysdr-module-rtlsdr など）を追加
cargo run --release -p jr-receiver-desktop
```

受信には `--release` ビルドを使ってください。`Cargo.lock` はリポジトリに含まれています。
GitHub Actions で Linux x86_64、Windows x64、macOS（Apple Silicon / Intel）向けの GUI・CLI バイナリをビルドします。
手動実行では成果物を作るだけです。`v1.7.0` のようにバージョンと一致するタグを push すると、GitHub Release にも公開します。
Windows 版には SoapySDR の DLL が同梱され、Linux / macOS 版はシステムにインストールされた SoapySDR 0.8 を使います。
ビルド、実行時の依存関係、CI、公開の手順は[リリースガイド](docs/RELEASE.ja.md)を参照してください。
ローカルでのビルドと起動は Linux でのみ確認しています。インストーラー、配布者の署名、公証はありません。

## 同時受信

[`ui/radio-presets.json`](ui/radio-presets.json) は、チャンネル定義と受信プロファイルを分けて記述した独自形式の JSON で、GUI と CLI が組み込みプリセットとして共用します。
デスクトップアプリは同じ形式の外部 JSON ファイルも読み込めます。再ビルドは不要です。
停止中に「受信設定」→「プリセットファイル」→「JSON ファイルを選択」から読み込みます。
編集を反映するには「再読み込み」、組み込みの 3 社に戻すには「組み込みに戻す」を選びます。

1. 入力方式を選びます。RTL-TCP では、サーバーの **IP アドレスとポート**を入力します（初回起動時は空欄です）。
   手元の SDR を使う場合は「SoapySDR デバイス」に切り替え、「検索」で機器を選びます。
   詳細設定では SoapySDR の引数、RX 番号、アンテナを指定できます。
2. 「受信設定」で受信プリセットを選び、チャンネル一覧で受信する波にチェックを入れます。初期状態は JR 東日本に割り当てられた 22 波です。
   **「路線から選ぶ」**を使うこともできます。路線名・駅名・D 番号で検索し、区間を（複数可）選んで周波数を確かめてから適用します。受信は「受信を開始」を押すまで始まりません。詳しくは[路線選択と外部ファイルへの路線情報の追加](docs/ROUTES.ja.md)を参照してください。
   組み込みプロファイルは JR 東日本（22 波）・JR 東海（3 波）・JR 西日本（19 波）の 3 種類で、それぞれ自社に割り当てられた周波数だけを含みます。
   一覧は**「簡易」表示**が初期値です。周波数・割当・同期状態をタイルで並べ、ウィンドウの幅に合わせて列数が変わります。
   「詳細」では形式と音声・データの件数を表で確認できます。表示の切り替えは受信・録音・選択波・検索に影響しません。
3. 初期値は中心周波数 **352.603125 MHz**、要求サンプルレート **240,000 S/s** です。
   入力欄の下のボタンで代表的なレートを選べます（RTL-TCP は 240k・288k・1.024M・2.048M・2.4M、SoapySDR は 240k・250k・1M・2.048M）。現在のレートのボタンは押された状態になります。
   レートが RTL-TCP の対応範囲外のときや、現在の中心周波数で受信対象の全波を復調するには足りないときは、その下に必要なレートを表示します。受信開始時には入力欄の値を検証します。
   SoapySDR では、機器から読み戻したレートと中心周波数で帯域を確認します。
   RTL-TCP は設定を読み戻せないため、要求した値をそのまま表示・使用します。
   プリセットを切り替えると、中心周波数と推奨レートも切り替わります。東日本・西日本は
   **352.603125 MHz**、東海は **352.625000 MHz** で、レートはいずれも **240 kS/s** です。
   IQ WAV 入力では、入力した中心周波数をプリセットの切り替えで変えません。
4. 「受信を開始」を押すと、チェックした全波の処理を始めます。アプリを起動しただけではサーバーに接続しません。
   周波数を選ぶと、その波の同期状態・EVM・コンスタレーション・データを表示します。
5. 「音声を聴く」で選択波の音声を再生します。**「通話を自動選択」**は初期状態でオンです。どちらのチェックボックスも受信バーにあり、スクロールしても操作できます。
   通話が重なったときは先に始まった通話を選び、それが終わると、続いている通話のうち最も早く始まったものに切り替えます。
   **周波数を手動で選ぶとその波に固定**し、モニタに「手動選択で固定中」と表示します。「通話を自動選択」をオンに戻すと自動切り替えを再開します。
   選択していない波も復号と音声合成を続けますが、再生するのは選択中の 1 波だけです。
6. 「録音・データ保存」の「保存内容・保存先」を開くと、WAV・生フレーム JSONL・データ電文 JSONL を選べます。
   「保存を開始」で、受信中の全波を保存します。初期状態で有効なのは WAV だけです。
   この欄を閉じても、状態と開始・停止ボタンは表示されたままです。

コンスタレーションと EVM は、受信フィルター・タイミング再生・搬送波補正・符号間干渉の除去を経た信号から求めます。
符号間干渉の除去には、系列検出器がその時点で最も確からしいとする伝送路推定を使います。表示は判定後の理想点ではなく、受信信号の振幅・位相のばらつきをそのまま示します。
EVM は調整の目安となる未校正の値で、SNR や誤り率の測定値ではありません。

周波数は 352.53750～352.66875 MHz の 6.25 kHz 間隔で、幅は 131.25 kHz です。
復調フィルターの余裕を含めると、全波の受信には 139.65 kS/s を超える複素サンプルレートが必要です。
機器の実効帯域やアンチエイリアス特性の分も余裕を見てください。
240 kS/s に非対応の機器では、1.024 MS/s など対応する高いレートを選んでください。
対応するハードウェアは、利用できる [SoapySDR のドライバー](https://github.com/pothosware/SoapySDR/wiki)によって決まります。

### 画面の構成

受信中によく見る情報ほど上に配置しています。上から、受信バー、受信の累計、受信設定、チャンネル一覧と選択波モニタ、運行把握モニタと受信データ、録音・データ保存の順です。

受信バーには、受信状態、「受信を開始」「停止」、選択波（周波数・割当・同期状態）、同期中の波数、保存状態、音声の 2 つのチェックボックスがあります。選択波は選択波モニタへ、保存状態は録音・データ保存の欄へのリンクです。
幅 36rem 超・高さ 36rem 以上の画面では受信バーを上端に固定し、リンク先やフォーカス先がバーに隠れないよう余白を取ります。狭い画面ではバーの割当名を省きます。
その下の 1 行に、受信帯域と、有効データ・音声フレーム・処理欠落の累計を表示します。
「受信設定」は停止中は開いており、受信を開始すると閉じます。閉じても見出しに受信プリセットと入力方式・接続先を表示します。
検索は一覧の表示を絞り込むだけで、受信対象は変わりません。
チャンネル一覧と選択波モニタは最初から開いています。選択波モニタは周波数と割当、受信状態の詳細、再生設定の順です。見出しを選ぶと折りたためますが、受信・音声再生・データ更新は続きます。
広い画面では運行把握モニタと受信データを横に並べ、その上に各欄へのリンクを置いています。受信データの欄には表示中の波を示し、そこからチャンネル一覧へ移動できます。
プリセットの読み込みに失敗したときや受信対象の指定に誤りがあるときは、該当する設定が自動で開きます。
「更新を一時停止」は受信データの表示だけを止め、復号と運行把握モニタの更新は続けます。狭い画面では、詳細表示の一覧をカード形式で表示します。

### 運行把握モニタ

「運行把握モニタ」は、JR 東日本の対応する共用波の電文から、線区ごとの遅延列車数・在線数・遅延時間帯別の件数・最大遅延とその列車番号を表示します。共用波を「一斉」形式で受信対象にしてください。
音声の選択、保存、受信データの一時停止とは独立して更新します。狭い画面では線区ごとに項目名を付けて表示し、提供されていない値は 0 ではなく「不明」と表示します。

電文に含まれる日時は、前置部の仕様が分かるまで解釈しません。表示するのは PC が最後に受信した日時だけで、ラベルは「最終受信日時（JST）」（IQ WAV の再生中は「最終読取日時（JST）」）です。この日時は情報が作られた日時ではなく、表の内容が現在の運行状況を表すとは限りません。前置部から情報の新しさや前後関係は判断しません。

結合と検証を終えた完全な表だけを受信順に反映します。前置部と表が前回と同じなら最終受信日時と受信回数を更新し、どちらかが変われば回数を数え直します。IQ が欠落しても直前の表と受信日時は残り、受信の再開始やプリセットの変更で消去します。

対応している形式は、確認済みの共用波 `0x22 / C9` 形式です。11 バイトの前置部と LH5 アーカイブからなり、展開後の `0x87` の表は 21 バイト × 7 行です。RS / CRC の検証と、アーカイブのヘッダー・内容の検査に通ったものだけを使います。一部だけ受信できたデータから別の形式を推測することはしません。

### RTL-TCP

RTL-TCP では IPv4 / IPv6 のアドレスを使えます。要求サンプルレートは 225001～300000 S/s または 900001～3200000 S/s です。
ゲインを空欄にするとチューナーの自動ゲイン、数値を入れると手動ゲインになります。周波数補正（ppm）は整数で指定します。
RTL-TCP は SoapySDR に代わるものではなく、Rust で実装した追加の TCP 入力です。
RTL-TCP はサーバー側の IQ 欠落や設定の拒否を通知しません。画面の「処理欠落」はアプリ内のワーカーキューで失われたブロック数の合計で、
サーバーがすべてのサンプルを届けたことを示すものではありません。

## 設定の保存

デスクトップアプリは設定の変更を自動で保存し、次回起動時に復元します。

- 入力方式、受信プリセット、中心周波数、サンプルレート、ゲイン
- 外部プリセットファイルのパス（使っている場合）
- RTL-TCP の IP アドレス・ポート・周波数補正
- SoapySDR のデバイス引数・RX 番号・アンテナ、IQ WAV ファイルのパス
- 保存のオン・オフ、保存先フォルダー、保存する形式

保存した中心周波数とレートは、起動時にプリセットの初期値で上書きされません。意図的に空欄にした項目も空欄のまま復元します。
起動時に復元するのは設定だけで、受信は開始ボタンを押すまで始まりません。保存がオンだった場合は、受信の準備が整うと保存も再開します。
ウィンドウを閉じるときは、直前の入力も含めて設定の書き込みが終わるのを待ちます。

設定は、Tauri のアプリ設定フォルダーにある `settings.json` に、バージョン付きの JSON として保存します。ソースコードやプリセットには書き込みません。

| OS | 保存場所 |
| --- | --- |
| Linux | `$XDG_CONFIG_HOME/io.jrradio.receiver/settings.json`（未設定の場合は `~/.config/io.jrradio.receiver/settings.json`） |
| macOS | `~/Library/Application Support/io.jrradio.receiver/settings.json` |
| Windows | `%APPDATA%\io.jrradio.receiver\settings.json` |

書き込みはまず一時ファイルに行い、完了してから元のファイルと置き換えます。書き込みに失敗した場合は、「保存を再試行」で最新の入力を保存できます。
ファイルが壊れている、または未対応のバージョンの場合は上書きせず、エラーにファイルの場所を表示します。
ファイルを修正するか別の場所に移してから、「設定を再読み込み」を選んでください。復元に失敗している間は、何も保存しません。
ブラウザーでのプレビューでは設定を保存しません。

## 通話の自動選択

通話の順番は、各通話の最初の有効な音声フレームを、全波で共通の IQ の時間軸上で比べて決めます。スレッドの実行順には左右されません。
同期の確立にかかる時間を見込んで 120 ms 待ってから判定し、同時の場合はプリセットでの並び順を優先します。
有効な音声フレームが **1 秒**途切れると、通話が終わったと判断します。音量や無音の PCM では判断しません。
受信が少し途切れただけなら優先順位は変わりません。待っている間に終わった通話は飛ばします。IQ の欠落や再同期があると、通話の状態をリセットします。
別の波に切り替えたときは直近 600 ms 以内の音声から再生し、たまっていた通話を最初から再生し直すことはしません。
この制限が適用されるのは、切り替えた直後と選択していない波です。同じ波を聴き続けている間は、RTL-TCP から約 0.5 秒分の入力がまとめて届いても、未再生の PCM を順番どおりに再生します。キューの上限は 5 秒のままです。
信号が一瞬途切れても、合成音声の末尾は最後まで出力します。手動で固定している間は、遅れて届いた自動選択の結果を反映しません。

## 録音・データ保存

状態が「受信中」になったら、「録音・データ保存」の **「保存を開始」**を選びます。
一度保存を始めると、再起動後も含めて以降の受信で自動的に保存します。受信の停止、IQ WAV の終端、アプリの終了ではオフになりません。オフにするには「保存を停止」（停止中は「保存を無効にする」）を選びます。この項目がない古い設定ファイルではオフとして扱います。自動での開始に失敗したときはエラーを表示して受信を続け、再試行はしません。
「保存内容・保存先」は最初は閉じています。開くと形式と保存先の選択、保存したフォルダーの確認ができます。
形式はそれぞれ個別に選べるので、JSONL だけを保存することもできます。形式を変えるときは、先に保存を停止してください。
エラーが起きると欄が開き、もう一度閉じてもエラーの内容は表示されたままになります。

初期の保存先は、OS のミュージックフォルダー内の `JR Conventional-line Radio Receiver/Recordings` です。
ミュージックフォルダーは、Windows では既定の「ミュージック」、macOS では `~/Music`、Linux では `XDG_MUSIC_DIR` を使い、取得できない場合は `~/Music` を使います。
以前の版では、製品名を誤って綴った `JR Cconventional-line Radio Receiver/Recordings` が初期値でした。保存先は設定に記録されるため、以前の版から引き継いだ設定ではそのフォルダーを使い続けます。
初期の保存先が存在しない場合は、録音の開始時に作成します。既存の別のフォルダーを選んだり、パスを入力したりもできます。
初期の保存先を特定・作成できない場合は録音欄にエラーを表示するので、別の保存先を選んでください。

チェックを入れた全チャンネルを録音します。表示中の波、検索結果、モニターの消音や音量には左右されません。
「保存を停止」を選んでも受信は続きます。受信の停止、IQ WAV の再生完了、アプリの通常終了でも録音を確定します。
停止した後は、別のフォルダーを選んで録音をやり直せます。

- 形式：**8 kHz・16 bit PCM・モノラルの WAV**。保存を始めた後に復号・合成した音声を記録します。
- 保存先：選んだフォルダーの中に、UTC 日時と重複防止の番号を付けた `recording-YYYYMMDDTHHMMSS.sssZ-NNN/` フォルダーを作ります。
  WAV のファイル名は `352537500Hz-000001.wav` のように周波数と連番です。既存のファイルは上書きしません。
- WAV は音声が得られた波についてだけ作ります。音声がなければ音声の件数は 0 のままですが、選んだ JSONL とセッション情報は保存します。
- 音声フレームの間隔が 5 秒以下なら無音で埋めます。5 秒を超える間隔、再同期、30 分の上限のいずれかで新しいファイルに切り替えます。
  各 WAV は最初の音声から始まるため、受信開始からの時間がそのまま続く録音ではありません。
- `session.json` には設定、`files.jsonl` には確定した各 WAV の周波数とフレーム範囲、`result.json` には終了時の結果を記録します。
- WAV のヘッダーはファイルの切り替え時か停止時に確定します。再生は録音を止めてから行ってください。
  録音中や異常終了の後には `INCOMPLETE` ファイルが残ります。強制終了や停電の後に自動で復旧する機能はありません。

書き込みは上限付きキューを持つ専用スレッドで行います。書き込みが追いつかないときや失敗したときは、エラーを表示して保存を止めます（受信とモニター再生は続きます）。
画面に表示する音声の秒数は全チャンネルの PCM の合計で、埋めた無音は含みません。経過時間とは異なります。

### JSONL の出力

選んだ場合、`raw-frames.jsonl` と `data-messages.jsonl` を同じセッションフォルダーに書き出します。
UTF-8 で 1 行に 1 つの JSON オブジェクトを書き、約 500 ms ごとと停止時にバッファを書き出して、正常終了時にファイルを確定します。
画面の履歴の上限、一時停止、重複のまとめ表示は出力に影響しません。同じ電文を何度受信しても、そのたびに保存します。

| ファイル | 内容 |
| --- | --- |
| `raw-frames.jsonl` | 同期器が切り出した 48 バイトの無線フレームを、受信した順に 96 桁の `raw_hex` として記録します。デスクランブルや誤り訂正の前の値で、音声・データの検証に失敗したフレームも含みます。IQ サンプルは含みません。 |
| `data-messages.jsonl` | 復号器が出力した電文ごとに 1 つの `message` を記録します。種別、識別子、送信日時（取得できた場合）、復号した項目、電文の `raw_hex`、フレーム範囲を含みます。音声チャンネルの情報や、解釈していない種別の電文も含みます。分割された電文は、結合が終わった時点で出力します。 |

運行把握電文は、`message.kind: "OperationSummary"` と追加の `message.operation_summary` で出力します。その `rows` には、`line`（線区）、`delayed`（遅延列車数）、`on_line`（在線数）、`delay_classes`（3～9 分・10～19 分・20 分以上の件数）、`max_delay_min`（最大遅延の分数）、`train_no`（列車番号）、行の元データの `raw_hex` が入ります。提供されていない値は `null` です。運行把握電文の `message.timestamp` は常に `null` で、外側の `received_at` が PC で復号した日時です。仕様が分かっていない前置部を日時として解釈・検証することはせず、受信日時で代用することもしません。`message.raw_hex` には結合後の圧縮された本文が、`prefix_hex` には前置部が、`expanded_hex` には展開後の表が入ります。`prefix_sum_matches` は観測されたバイトの合計値の関係が成り立つかを示すだけです。プロトコル上の意味は確認できていないため、検証済みのチェックサムとしては扱いません。

どちらのファイルにも、`schema_version: 1`、`received_at`、`channel_id`、`label`、`frequency_hz`、`format`、`epoch`、`index`、`bit_offset` が入ります。
`received_at` は復号した時点の PC の UTC 時刻で、送信側の時計ではありません。
`index` はチャンネルの epoch 内での 40 ms 単位のフレーム番号です。`bit_offset` は同期器の区間内でのビット位置で、IQ の欠落でリセットされます。
生フレームには、`sync_matched`、`marker_errors`、`voice_accepted`、`corrected_bits`（音声として受理した場合のみ数値）も入ります。
電文の行のフレーム位置は、その電文を出力したフレームを指します。
同じチャンネル内では処理した順に並びますが、チャンネルをまたいだ行の順序は受信時刻の順になるとは限りません。
`session.json` の `outputs` には保存する形式を、`result.json` には生フレーム数・電文数とエラーを記録します。
書き込みエラーや保存キューのあふれが起きると、セッション全体の保存を止め、`INCOMPLETE` を残して画面にエラーを表示します。

## IQ 録音の再生と CLI

GUI で入力方式を「IQ WAV ファイル」にすると、選んだ全波をリアルタイムで復号します。
対応形式は、ステレオの float32 または PCM16 の RIFF/WAVE（左が I、右が Q）、サンプルレート 9.6 kS/s～20 MS/s です。
サンプルレートは WAV のヘッダーから読み取ります。**録音したときの中心周波数は手で入力**してください。
RF64 や、4 GiB を超えて RIFF の長さが一周した WAV は読み込めません。通常の RIFF/WAVE に分割・変換してから読み込んでください。

```sh
# SDR の一覧 / 周波数プリセットを JSON で出力
cargo run --release -p jr-receiver -- devices
cargo run --release -p jr-receiver -- presets east
cargo run --release -p jr-receiver -- presets --list
cargo run --release -p jr-receiver -- presets central

# 環境変数 RTL_TCP_ENDPOINT にサーバーの IP アドレスとポートを設定して実行
# 全 22 波を 60 秒間受信し、統計を JSON で出力して切断
cargo run --release -p jr-receiver -- \
  monitor-tcp "${RTL_TCP_ENDPOINT:?接続先の IP アドレスとポートを設定してください}" 60 240000 352603125 east

# WAV ヘッダーの確認
cargo run --release -p jr-receiver -- inspect-wave input.wav

# 全 22 波をファイルに復号。末尾の 10 は処理する秒数（省略すると全体）
cargo run --release -p jr-receiver -- \
  decode-wave input.wav 352600000 new-output east 10

# 保存した frames.bin / indices.txt から音声とデータを復号
cargo run --release -p jr-receiver -- \
  decode-frames captured-stream new-decoded-output slotted
```

出力先には、まだ存在しないディレクトリを指定してください。周波数ごとに `audio.wav`（8 kHz・モノラル・PCM16）、
`data.jsonl`（検証を通った電文の全受信記録）、`messages.json`（直近最大 128 件をまとめたもの）を保存します。
`decode-frames` は、WAV と JSONL を `stream/` の下に、`report.json` を最上位に出力します。
先頭と末尾に無音は付けません。音声フレームの間の欠落は無音として残します。
同期のビット位相が変わってストリームが分かれた場合は連結し、その境目を report の epoch に記録します。
失敗や中断の後には `INCOMPLETE` が残ります。`report.json` には、波ごとの受理・拒否・訂正の件数と処理時間が入ります。
CLI でのファイルの復号は、処理が追いつくまで読み込みを待たせることで入力の欠落を防ぎます。ライブ受信と違い、リアルタイム処理は保証しません。

SoapySDR を使わずに、ファイルの復号と RTL-TCP 入力だけをビルドすることもできます。

```sh
cargo run --release -p jr-receiver --no-default-features -- --help
```

### 復調器の評価（合成信号・開発用）

開発用ツール `jr-demod-eval`（`crates/demod-eval`）は、録音データを使わずに復調器の性能を測ります。製品（デスクトップアプリと `jr-receiver`）やリリースには含まれません。受信コアのフレーム符号化器は `synthesis` 機能を有効にしたときだけビルドされ、このツールがそれを有効にします。乱数のペイロードで音声フレームを符号化し、π/4-DQPSK（4,800 symbols/s、ロールオフ率 0.2 のルートレイズドコサイン）で変調します。これを合成した伝搬路に通し、実際の受信と同じ DSP・フレーム同期・音声復号器で受信します。
伝搬路はタップ付き遅延線モデルで、経路ごとの遅延・電力・周波数差（`--paths 遅延µs:電力dB[:周波数差Hz]`）、最大ドップラー周波数（0 で静的）、先頭経路のライス係数（任意）、搬送波オフセット、白色ガウス雑音を指定できます。フェージングは Clarke モデルの正弦波合成で、平均電力を 1 に正規化しています。Es/N0 は平均受信電力を基準にします。

```sh
# 静的な 2 波（52 µs 遅延）と、ドップラー 40 Hz のレイリーフェージング（時速約 120 km 相当）
cargo run --release -p jr-demod-eval -- \
  --es-n0 10,14,18,22,26,30 --paths 0:0,52:0 --frames 400 --seeds 3
cargo run --release -p jr-demod-eval -- \
  --es-n0 10,14,18,22,26,30 --doppler 40 --frames 400 --seeds 3
```

Es/N0 ごとの要約を標準エラーに、JSON を標準出力に出力します。主な項目は次のとおりです。

| 項目 | 意味 |
| --- | --- |
| `symbol_error_rate` / `bit_error_rate` | 誤り訂正前の差動シンボル誤り率とビット誤り率。送信系列とブロックごとに位置を合わせて数えます。位置を合わせられないブロックは `symbols_unaligned` に数えます |
| `voice_acceptance` | 送信した音声フレームのうち、保護ビットが正しく受理されたものの割合 |
| `voice_false` | 保護ビットが送信内容のどれとも一致しないのに受理されたフレーム（検出できなかった誤り） |
| `alternate_accepted` | 副系統（RLS）のフレームでしか復号できず、それを採用したフレームの数。`--single` を付けると副系統を使わずに比較できます |
| `clock_slips` | 受信側でシンボルが抜けたり重複したり（クロックスリップ）した回数。ブロック間の位置合わせの変化から数えます |
| `data_accepted` / `data_false` | `--traffic data` のとき、28 バイトの情報部を正しく復元できたデータフレームの数と、送信していない内容で受理されたフレームの数 |
| `unprotected_bit_errors` | 受理したフレームのうち、無線方式で保護されていない 80 ビットに生じた誤り |
| `fade_bins` | 各シンボルの中心における瞬時の伝搬路電力（平均との比）ごとのシンボル数と誤り数。−20 / −10 / −5 / 0 dB で区切ります。誤りがフェージングの落ち込みに集中しているか（雑音が原因）、強い信号でも残るか（追従が原因）を見分けられます |

経路ごとに周波数差を付けると、複数の基地局が同じ周波数で同時に送信する状況を再現できます。各局の搬送波のわずかな差でビートが生じ、到着時刻もずれます。たとえば `--paths 0:0,208:0:5` は、2 局目が 1 シンボル遅れ、5 Hz ずれた同じ電力の 2 局を表します。
`--traffic data` はデータフレーム（RS(42,30) と CRC-16）を送ります。`--hard` は軟判定の信頼度を使わずに復号するため、同じビルドで軟判定の効果を比べられます。
`--receiver differential` は比較用の基準検波器です。既知のシンボルタイミングで整合フィルターを通し、遅延検波します。追従を必要としないため、同じ伝搬路で非同期検波がどこまで受信できるかの目安になります。実際の受信には使いません。
最初の 3 フレームは同期の引き込みに使うため、集計から除きます。結果は乱数シードごとに再現できます。

## 実装と検証

- `crates/jr-conventional-dsp`：周波数変換、フィルター、タイミング・搬送波同期、等化を担う DSP。系列検出器は 2 系統あります。主系統は LMS で伝搬路を追従します（雑音に強く、静止時や低 SNR に向きます）。副系統は各タップの値とその変化率を RLS で推定し（等速モデル）、時間とともに速く変わる伝搬路に追従します。複数の基地局が同じ周波数で送信する区間を列車が走る場合などです。副系統は専用の搬送波ループを持ち、両系統は同じ遅延で判定を出力します。どちらも硬判定に加え、ビットごとの信頼度（軟判定）を出力します。信頼度は、符号間干渉を除いた受信値を伝搬路推定で重み付けした差動積から求めるので、フェージングの落ち込みでは小さくなり、信号を見失った区間では 0 になります。
- [`crates/jr-voice`](crates/jr-voice/README.md)：Rust だけで実装した CELP 音声合成（バージョン 1.3.0）。現フレームと次フレームの合成候補を比較し、先読みは合計 7 フレーム（280 ms）です。`src/models/` にある固定のモデル係数は実行ファイルに組み込まれます。
- `crates/receiver-core`：同期、音声チャンネルの復号、RS / CRC、データの組み立て、LH5、日本語・英語テキスト、SoapySDR / RTL-TCP、同時受信のワーカー。
  2 系統の判定列はそれぞれ別にフレーム同期を取り、同じ時間帯のフレーム（開始位置の差が半フレーム未満）を組にします。主系統のフレームが音声かデータとして復号できればそれを使い、できなければ副系統のフレームが復号できる場合にそちらを使います。採用したフレームは 384 ビット単位の位置にそろえます。副系統を採用した数は、状態の `alternate_frames` で確認できます。2 系統を動かすため、1 波あたりの CPU 負荷はおよそ 2 倍になります。
  フレーム同期では、128 ビットの各区間の先頭にあるマーカーを確認し、タイミングのずれでシンボルが 1 つ増減した区間は 1 シンボルずらして合わせ直します。同期を失って 3 フレームかけて引き込み直す代わりに、残りの区間と後続のフレームを生かします。出力するビット位置は 384 ビット単位のままです。
  硬判定の復号器で受理できなかったフレームは、信頼度を使ってもう一度復号します。音声は軟判定ビタビ復号を行い、末尾の Reed–Solomon 符号は信頼度の低いバイトを最大 6 個まで消失として訂正します。データは信頼度の低いバイトを最大 8 個まで消失として RS(42,30) を復号します。受理の条件は変わらず、CRC の一致と、音声では末尾の CRC-16・RS パリティの一致が必要です。
- `src-tauri` / `ui`：日本語の GUI、受信の操作、選択波の Web Audio での再生。
- `crates/receiver-cli`：デバイスの一覧、RTL-TCP の受信テスト、IQ / フレームファイルの復号。
- `crates/demod-eval`：合成信号と合成伝搬路で復調器を評価する開発用ツール。製品やリリースには含まれません。

IQ は一度だけ取得し、参照カウント付きのバッファで各チャンネルの上限付きキューに渡します。
各チャンネルは DSP・同期・音声・データの状態をそれぞれ持ち、別々のスレッドで処理します。
ソースのオーバーフローやキューでの欠落を検出すると、そのストリームの連続性を捨てて同期を取り直します。
IQ のキューは各波 8 ブロックです。TCP 入力のキューはバーストを吸収するために 32 ブロック（240 kS/s で最大 1.28 秒分）あります。
TCP のヘッダーは 3 秒、ストリームのデータは 5 秒届かなければエラーにします。切断と正常な終了は区別します。
画面の状態は約 180 ms ごとに更新します。データの履歴は各波 128 件まで、音声モニターのキューは 5 秒までです。
リアルタイム再生は 440 ms のジッターバッファをためてから始め、画面の更新より先に、音声出力の時計に合わせて PCM を途切れなく再生予約します。到着が少し遅れても、再生中の音声は止めません。線形補間の直前のサンプルと小数部の位置を 40 ms の PCM フレームをまたいで引き継ぎ、受信側と出力側の時計のずれもこのリサンプラーで少しずつ補正します（最大 ±0.5%）。Web Audio には出力機器と同じサンプルレートのバッファを渡し、再生速度を 1 に固定したまま、サンプル単位の境界で続けて再生します。これにより、フレームごとの補間のやり直しや、端数による境界のノイズを防ぎます。まとめて届く入力や更新間隔のばらつきを吸収できるよう、再生予約は最大 1.5 秒までです。これらの調整はモニター再生だけのもので、録音する WAV のサンプルには影響しません。
停止時には取得スレッドと処理スレッドの終了を待ち、再開時には状態を新しく作り直します。

```sh
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --exclude jr-receiver-desktop
cargo build --release -p jr-receiver-desktop
npm ci
npm test  # 入力検証と DOM の状態遷移のテスト（描画結果は検証しません）
node scripts/check-contrast.mjs
```

Linux で実際の再生波形を確かめるには、`python3-gi`、`gir1.2-webkit2-4.1`、ディスプレイ環境（なければ `xvfb-run`）を用意して、`/usr/bin/python3 scripts/check-audio-webkit.py` を実行します。合成した一定値と正弦波の PCM を WebKitGTK で 44.1・48・96 kHz で出力し、時計のずれを補正した状態でフレームの境界がつながっているかを確認します。失敗すると 0 以外の終了コードを返します。スピーカーから音は出さず、録音データも使いません。同じ[テストページ](tests/audio/playback-render.html)をローカルで配信すれば、他のブラウザーでも確認できます。
